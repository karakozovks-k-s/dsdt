# Гайд: как настроить Hermes + DeepSeek так, чтобы агент писал код близко к уровню Claude Code

Этот документ — самонастраивающаяся инструкция. Агент должен прочитать её
целиком, выполнить чек-лист в конце и поддерживать описанные инварианты во
время работы.

> Источники, на которые опирается гайд:
> - Hermes Agent — https://github.com/nousresearch/hermes-agent
> - DeepSeek API — https://api-docs.deepseek.com/
>
> Если в актуальной доке DeepSeek параметр называется иначе, чем здесь
> (особенно для модели «V4 Pro», название которой публично не подтверждено
> на момент написания) — побеждает дока, не этот файл. Всегда сверяйтесь.

---

## 0. Философия

Качество кодинг-агента почти не зависит от «насколько умная модель». Оно
зависит от четырёх вещей:

1. **Инструменты.** Edit/Read/Grep отдельными тулзами вместо `bash -c`.
2. **Обратная связь.** Линтер, тайпчекер и тесты, запускаемые автоматически
   после каждой правки, чтобы агент видел свои ошибки.
3. **Контекстная гигиена.** Не таскать в контекст лишние файлы. План и
   TODO держать в структурированном виде, а не «в голове модели».
4. **Жёсткий системный промпт.** Запреты должны быть явными: не выдумывать
   API, не писать «комментарии-что-делает-код», не делать деструктивных
   операций без подтверждения.

Дальше — конкретика по каждому пункту под Hermes + DeepSeek.

## 1. Базовая настройка модели

### 1.1. Выбор модели

В Hermes модель выбирается через `hermes model` или `hermes config set`.
Для кодинга:

- **Основная модель** — самая сильная reasoning-модель DeepSeek, доступная
  через ваш ключ (`deepseek-reasoner` или то, что у вас идёт под именем
  «V4 Pro»). Используется для планирования и сложных правок.
- **Быстрая модель** — `deepseek-chat` (V3-семейство). Используется для
  механических задач: переименования, форматирование, тривиальные правки.
- Если Hermes поддерживает «двухмодельный» режим (роутинг по сложности) —
  включите его. Если нет — задайте reasoning-модель основной, а быструю
  вызывайте явно через под-агента.

### 1.2. Параметры инференса

| Параметр       | Значение для кода          | Почему                                |
|----------------|----------------------------|----------------------------------------|
| `temperature`  | `0.0`                      | DeepSeek официально рекомендует 0 для кода. |
| `top_p`        | `0.95` (или дефолт)        | Не трогайте, если не понимаете зачем. |
| `max_tokens`   | максимум, что разрешает API (≥ 8192) | Иначе диффы и патчи рвутся посередине. |
| `stream`       | `true`                     | Чтобы Hermes мог рано прерывать на ошибке. |
| reasoning/thinking | включить, если модель поддерживает | Для архитектурных шагов и отладки. |
| `stop`         | не задавать                | Hermes сам управляет окончанием. |

### 1.3. Prompt caching

DeepSeek кеширует общий префикс запросов автоматически (Context Caching on
Disk). Чтобы это работало:

- **Системный промпт держите неизменным внутри сессии.** Любая правка
  системного промпта инвалидирует кеш.
- **Стабильный блок** (правила, конвенции репо, дерево каталогов) кладите
  в начало контекста, динамику (текущий файл, последний tool result) — в
  конец.
- Не вставляйте timestamp/uuid в системный промпт.

## 2. Системный промпт

Положите этот текст в `~/.hermes/personalities/coder.md` (или эквивалент
вашего конфига) и сделайте его дефолтной личностью через
`hermes personalities`.

```text
Ты — кодинг-агент. Твоя задача — вносить корректные, минимальные,
проверяемые изменения в кодовую базу пользователя.

# Жёсткие правила

1. ПЕРЕД редактированием файла ВСЕГДА читай его целиком (или нужный
   диапазон строк). Никогда не правь файл «по памяти».
2. НЕ ВЫДУМЫВАЙ API, имена функций, поля, флаги CLI. Если не уверен —
   проверь grep/Read или открой документацию через web-fetch.
3. Не пиши комментарии вида «// увеличиваем счётчик» — они описывают ЧТО,
   а не ПОЧЕМУ. Комментарий уместен только если объясняет неочевидное
   решение, инвариант, обход бага или внешнее ограничение.
4. Не добавляй обработку ошибок, фолбеки и валидацию для случаев, которые
   не могут произойти. Доверяй внутреннему коду. Валидируй только на
   границах системы (ввод пользователя, внешние API).
5. Предпочитай редактировать существующие файлы созданию новых. Не плоди
   README/доки без явной просьбы.
6. Не делай рефакторинг, выходящий за рамки задачи. Три похожих строки
   лучше преждевременной абстракции.
7. Перед деструктивной операцией (`rm -rf`, `git reset --hard`,
   `git push --force`, drop table, удаление веток) — спроси подтверждения.
8. Если упёрся в ошибку — НЕ глуши её и не добавляй `--no-verify`. Найди
   причину.

# Workflow

Для любой нетривиальной задачи:

1. Прочитай задачу. Если что-то неоднозначно — задай уточняющий вопрос.
2. Построй TODO-план через тулзу `todo`. Один пункт = одно атомарное
   изменение, проверяемое тестом или запуском.
3. Изучи релевантные файлы через grep/glob/read, ПРЕЖДЕ чем писать код.
4. Делай минимальную правку → запускай линтер/тесты → переходи к
   следующему пункту.
5. По завершении: краткое резюме (что изменилось, что дальше). Без воды.

# Tone

- Отвечай коротко. Без преамбул «Конечно, я с радостью...».
- Не дублируй в тексте то, что и так видно в diff.
- Не используй emoji, если пользователь не попросил.
```

> Этот промпт намеренно срисован с правил Claude Code. Его сила не в
> формулировках, а в том, что модель РЕГУЛЯРНО получает их в контексте и
> обучается на них через RLHF-следование инструкциям.

## 3. Инструменты (tools)

Через `hermes tools` оставьте включёнными только те, что нужны для
кодинга. Шум от лишних тулз снижает качество вызова нужных.

### 3.1. Минимальный must-have

- `read_file` — с поддержкой чтения по диапазону строк и нумерацией.
- `edit_file` / `apply_patch` — точечная замена, НЕ перезапись файла
  целиком. Если в Hermes есть только «write», добавьте через MCP
  отдельный edit-сервер (см. §8).
- `write_file` — только для НОВЫХ файлов.
- `grep` — отдельная тулза с regex и `--include`.
- `glob` — поиск по паттерну.
- `bash` — для всего остального (тесты, линтер, git).
- `todo` / task list — структурированный план.

### 3.2. Что выключить для кодинга

- Браузер-автоматизация, картинки, голос — отвлекают.
- «Универсальный» retrieval по всему интернету — включайте только когда
  явно нужна дока.

### 3.3. Правила вызова

В системном промпте добавьте раздел tool-policy:

```text
# Использование инструментов

- Для чтения файлов используй ТОЛЬКО `read_file`, не `bash cat`.
- Для редактирования — ТОЛЬКО `edit_file`, не `bash sed`.
- Для поиска — `grep`/`glob`, не `bash find ... -exec grep`.
- Независимые вызовы делай параллельно в одном шаге.
- Никогда не запускай `cd`. Используй абсолютные пути.
- Перед запуском долгого процесса — оцени таймаут и выставь явно.
```

## 4. Hooks и автоматизация

Hermes поддерживает cron-планировщик и хуки. Минимальный набор для
кодинга:

### 4.1. After-edit hook

После каждого `edit_file`/`write_file` агент должен видеть результат
автоматических проверок. Конфигурируется в `~/.hermes/hooks/`:

```yaml
# ~/.hermes/hooks/after_edit.yaml
trigger: tool_result
match_tool: ["edit_file", "write_file"]
run: |
  # Подставьте команды вашего проекта
  ruff check {file} || true
  mypy {file} || true
script_output_to_agent: true
```

Без этого хука агент не узнает, что сломал тайпы — пока не запустит
тесты вручную (а он их часто «забывает»).

### 4.2. Pre-commit hook

```yaml
# ~/.hermes/hooks/pre_bash.yaml
trigger: tool_call
match_tool: bash
match_command_regex: "^git commit"
run: |
  pytest -x --timeout=60
block_on_failure: true
```

### 4.3. Запреты деструктива

```yaml
# ~/.hermes/hooks/safety.yaml
trigger: tool_call
match_tool: bash
match_command_regex: "(rm -rf|git push --force|reset --hard|drop table)"
require_user_confirmation: true
```

## 5. Skills (самописные навыки Hermes)

Hermes умеет создавать скилы автономно. Принудительно засейте полезные
для Python-кодинга:

```bash
hermes skills add python-test-runner
hermes skills add ruff-fix
hermes skills add gh-pr-review
```

Скил — это просто markdown-инструкция + опциональный Python RPC. Шаблон
полезного скила:

```markdown
---
name: python-test-runner
description: Запустить pytest для изменённых файлов, вернуть только
  упавшие тесты с traceback.
trigger: после правки *.py
---

1. Определи изменённые файлы через `git status --porcelain`.
2. Найди соответствующие тестовые файлы (`test_<имя>.py` или
   `tests/test_<имя>.py`).
3. Запусти `pytest -x --tb=short <файлы>`.
4. Верни только упавшие тесты, не весь stdout.
```

Этот паттерн «скил = небольшая процедура, скрывающая шум» — главный
рычаг качества: модель не тратит токены на парсинг тонн вывода.

## 6. Контекст и память

### 6.1. Project context file

В корне проекта создайте `AGENT.md` (или подключите как project context
через `hermes config set project_context AGENT.md`). Туда:

- Команды: `make test`, `make lint`, `make run`.
- Стек: Python 3.12, Poetry, FastAPI, Postgres 16.
- Конвенции: «функции в snake_case, классы в PascalCase, никаких
  print — только logger».
- Табу: «не трогай миграции в `alembic/versions/`», «не правь
  `generated/`».
- Точки входа: где главный модуль, где роуты, где модели.

Этот файл должен быть **коротким** (≤ 200 строк). Иначе он съедает
контекст и кешируется хуже.

### 6.2. Сессионная память

Hermes хранит сессии в FTS5. Полезные привычки:

- В конце каждой задачи — одна строчка summary через `hermes session
  note`. Потом ищется грепом.
- Решения по архитектуре — отдельным файлом в `docs/decisions/` с датой,
  не в памяти агента.

### 6.3. Компакция

Если Hermes поддерживает auto-compact — включите с порогом ~70% окна
DeepSeek. Если нет, в системный промпт добавьте: «Если контекст близко
к лимиту, сделай summary текущего состояния и попроси пользователя
начать новую сессию с этим summary».

## 7. MCP-серверы (буст качества)

Hermes — нативно MCP-совместим. Подключите минимум эти серверы:

| MCP-сервер             | Зачем                                      |
|------------------------|---------------------------------------------|
| `mcp-language-server`  | LSP для Python: go-to-def, find-references, диагностика. Серьёзно меняет качество. |
| `mcp-github`           | Чтение PR/issues/CI без `gh` в bash.       |
| `mcp-fetch`            | Чистый markdown с веб-страниц для чтения доки. |
| `mcp-filesystem`       | Если встроенный edit слабый — берите отсюда. |
| `mcp-postgres` / `mcp-sqlite` | Только read-only для отладки запросов. |

Конфиг кладётся в `~/.hermes/mcp.json` (название уточните в `hermes
doctor`). Пример:

```json
{
  "mcpServers": {
    "lsp-python": {
      "command": "uvx",
      "args": ["mcp-language-server", "--lang", "python"]
    },
    "fetch": {
      "command": "uvx",
      "args": ["mcp-server-fetch"]
    }
  }
}
```

## 8. Под-агенты и параллельность

Hermes умеет спавнить изолированных под-агентов. Используйте их для:

- **Широкий поиск** (`explore`-агент): «найди все места, где
  используется этот эндпоинт». Возвращает список путей и строк, не
  засоряя основной контекст.
- **План** (`plan`-агент): получает задачу, возвращает 5–10 шагов,
  завершается. Основной агент исполняет.
- **Параллельные независимые правки**: например, обновить версию
  библиотеки в трёх независимых модулях.

Правило: под-агент = свой контекст. Возвращает короткое резюме, а не
дамп прочитанного.

В системный промпт добавьте:

```text
Если задача требует чтения > 5 файлов для исследования или поиска
по всему репо — делегируй под-агенту explore. Если задача делится на
независимые шаги — запусти их параллельно.
```

## 9. Цикл работы (loop)

Жёстко закрепите в промпте:

```text
ЦИКЛ для каждой задачи:

(1) PLAN     — план через todo, 1–10 пунктов.
(2) LOCATE   — grep/glob/read, чтобы найти место правки.
(3) EDIT     — минимальная правка через edit_file.
(4) VERIFY   — линтер + тесты через bash. Не «я думаю, должно работать»
               — а реально запустил.
(5) ITERATE  — если красное, идёшь в (3). Если зелёное — следующий
               todo.
(6) REPORT   — короткое резюме: что сделал, что дальше.
```

Если Hermes поддерживает state-машину агента — закодируйте этот цикл
явно. Если нет — пунктом в промпте достаточно, при temperature=0
модель его соблюдает.

## 10. Git и безопасные операции

В Hermes hook-конфиге (см. §4.3) уже стоит require-confirmation на
деструктив. В системный промпт добавьте git-policy:

```text
# Git

- Никогда не пушь без явной просьбы пользователя.
- Никогда не делай force push в main/master.
- Не используй --no-verify, --no-gpg-sign.
- Создавай новые коммиты, не amend, если пользователь не попросил.
- Перед `git add .` подумай, не попадут ли .env, секреты, артефакты.
- Сообщения коммитов: первая строка ≤ 72 символа, повелительное
  наклонение, объясняй ПОЧЕМУ, а не ЧТО.
```

## 11. Эвалы (без них всё бессмысленно)

Любая «улучшилка» — линтер-хук, новый промпт, смена модели — должна
проверяться на одном и том же наборе задач. Иначе вы тюнингуете
плацебо.

### 11.1. Соберите эвал-сет

10–20 реальных задач из своего репо:

- 5 багфиксов (с известным правильным фиксом).
- 5 фич (мелких, ≤ 50 строк дифф).
- 3 рефакторинга.
- 2 «нерешаемых» (агент должен сказать «недостаточно информации»,
  а не выдумать).

Положите в `evals/tasks/*.md`, ожидаемый результат — в
`evals/expected/*.diff` или как pytest-проверка.

### 11.2. Запуск

```bash
hermes eval run evals/
```

Если у Hermes своего раннера нет — простой Python-скрипт, который:
1. Создаёт чистый воркспейс из git-снапшота.
2. Запускает агента с задачей.
3. Сравнивает результат (тесты проходят? diff в нужных файлах?).
4. Считает pass-rate.

Запускайте после каждого изменения настроек. Цель — pass-rate не
падает. Без этого вы не знаете, помог ваш «улучшающий» промпт или
сломал.

## 12. Чек-лист самонастройки

Агент должен пройтись по этому списку при первом запуске после
прочтения гайда. Каждый пункт — `bash`-команда или ручная проверка.

- [ ] `hermes doctor` — нет ошибок.
- [ ] `hermes model` — основная модель = reasoning-модель DeepSeek.
- [ ] `hermes config get temperature` = `0`.
- [ ] `hermes config get max_tokens` ≥ `8192`.
- [ ] `~/.hermes/personalities/coder.md` существует и активна.
- [ ] `hermes tools list` — включены: read/edit/write/grep/glob/bash/todo.
       Выключены: браузер, картинки, голос.
- [ ] `~/.hermes/hooks/after_edit.yaml` — настроен ruff/mypy.
- [ ] `~/.hermes/hooks/safety.yaml` — деструктив требует подтверждения.
- [ ] `~/.hermes/mcp.json` — подключён LSP-сервер.
- [ ] В корне проекта есть `AGENT.md` ≤ 200 строк.
- [ ] `evals/tasks/` содержит ≥ 10 задач, прогон даёт baseline pass-rate.
- [ ] Тестовый прогон: «добавь функцию X с тестом» — агент сначала
       читает файл, потом правит, потом запускает тест, потом отвечает.
       Если он сразу пишет код без чтения — промпт не работает,
       проверьте, что personality активна.

## 13. Что НЕ поможет (анти-паттерны)

- **Длинные многословные системные промпты с примерами на 500 строк.**
  Модель их игнорирует после первых ~1000 токенов. Жёсткие короткие
  правила работают лучше.
- **«Творческая» температура для кода.** Любое значение > 0.3 даёт
  галлюцинации API.
- **Один мега-инструмент `bash` вместо отдельных тулз.** Модель путается
  в экранировании и теряет структурный вывод.
- **Закидывание всего репо в контекст.** Качество падает, цена растёт.
  Используйте grep + чтение по диапазону строк.
- **Автоматический `git push` после каждой правки.** Один раз снесёт
  работу — больше не захотите.
- **Слепое доверие отчётам агента.** Всегда проверяйте `git diff`
  глазами перед коммитом.

## 14. Что делать, когда всё равно хуже Claude Code

Реалистично: даже идеально настроенный Hermes + DeepSeek будет
отставать от Claude Code на сложных задачах, потому что разница не
только в обвязке, но и в самой модели (Anthropic тренировал Claude
специально под tool-use в кодинге). Стратегия:

1. Используйте DeepSeek как «дешёвую массовую лошадь» — генерация
   бойлерплейта, тесты, рефакторинги.
2. Сложные архитектурные шаги делайте через reasoning-модель с
   увеличенным thinking-бюджетом.
3. На критичных PR — добавьте второй проход через Claude/GPT через
   OpenRouter (Hermes это поддерживает) как ревьюера. Дёшево и
   ловит регрессии.
